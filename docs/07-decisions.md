# 7. Decisions and measurements

Every significant choice, what it cost, and what it bought. Where a number
exists it is quoted; where one does not, that is said plainly rather than
dressed up.

## The two bugs that mattered most

Both were found by measurement, not by reading the code. Together, on the
fixed 40-question sample used for iteration, they moved BIRD accuracy from
42.5% to 50.0%, eliminated context failures entirely (9 of 40 → 0), dropped the
repair rate from 22.5% to 0%, and cut mean latency from 6.3s to 2.5s.

The same pipeline then scored **56.7% on a 150-question sample**.

### Bug 1: case-sensitive table matching

**Symptom.** A quarter of all benchmark failures were
`Query references table(s) not provided in the schema: player, match` — on
databases that plainly contained `Player` and `Match`.

**Cause.** The validator lowercases table names parsed out of SQL, because SQL
identifiers are case-insensitive. It then compared them against the allow-list,
which kept its original case:

```python
tables = {"player", "match"}                  # parsed, lowercased
allowed_tables = {"Player", "Match", ...}     # from the schema, original case
unexpected = {t for t in tables if t not in allowed_tables}   # → everything
```

Every correct query against a capitalised schema was rejected. The repair loop
then burned its whole budget regenerating queries that were right the first
time.

**Fix.** One line:

```python
permitted = {name.lower() for name in allowed_tables}
```

**Why it survived 187 passing tests.** Every fixture used lowercase table
names, which is the PostgreSQL convention. The bug only appears against
schemas that capitalise — a convention common in SQL Server, and in anything
generated by an ORM. It took running against eleven real third-party databases
to surface.

The lesson is not "write more tests". It is that fixtures share the blind spots
of whoever wrote them, and only unfamiliar data finds those.

### Bug 2: Loop B never fired for its cheapest trigger

**Symptom.** A test asserted the schema walk widened after a missing-table
failure. It did not.

**Cause.** The widening decision only inspected `ExecutionError`. But the
validator's allow-list catches "table not provided" *first*, before any
database round trip, and raised `ValidationError` — which the pipeline treated
uniformly as "the SQL was wrong", the Loop A case.

So the single most common context failure, detected by the cheapest possible
check, never triggered the mechanism built to handle it.

**Fix.** Classify validation errors too, and make the loop decision in one
place that both paths reach:

```python
CONTEXT_FAILURES = frozenset({"table_not_allowed", "missing_relation", "missing_column"})
```

**The design lesson.** A branch condition that inspects an exception *type*
rather than an error *classification* will silently miss any new path that
raises a different type. The kinds now live in one named set.

## Model selection

Chosen by measurement. BIRD mini-dev, 150 questions, fixed seed, identical
pipeline:

| Model | Accuracy | Time/question | simple | moderate | challenging |
|---|---|---|---|---|---|
| **qwen.qwen3-coder-480b-a35b-instruct** | **56.7%** | **2.5s** | 73% | 51% | 44% |
| qwen.qwen3-coder-next | 52.0% | 4.1s | 65% | 51% | 32% |
| deepseek.v3.2 | 49.3% | 4.0s | 67% | 42% | 40% |

The largest model was also the **fastest**, by roughly 1.6×. That is unusual
and it removes the trade these decisions normally involve: there was no
accuracy-versus-latency choice to make.

**Consequence: both tiers point at the same model.** A tiering scheme exists in
the configuration — light for classification and phrasing, strong for hard
joins — but honouring it here would mean deliberately choosing a model that is
worse on *both* axes. The split is kept because it costs nothing and becomes
useful the moment a cheaper model is worth its accuracy loss: a different
provider, a different scale, or a cost ceiling.

An earlier 40-question round also tested `zai.glm-5` (35.0%, 82s per question).
Less accurate and dramatically slower; dropped.

### What is *not* available

Mantle lists 54 models. Ten are callable on this account. Anthropic's Claude
models and OpenAI's GPT-5 family appear in the catalogue and return
`not available for this account` when invoked — entitlement is separate from
listing. Claude additionally rejects `/v1/chat/completions` and is served at
`/anthropic/v1/messages`, which is worth knowing before concluding a model is
broken.

This is why `python -m sqlagent.cli --models` exists: the only reliable way to
know what you can call is to call it.

## Sending the whole schema on small databases

**Decision.** At or below 15 tables, skip retrieval entirely.

**Why.** Graph retrieval exists because a large schema does not fit in a
prompt. On a six-table database it is pure overhead — and worse, if seed
selection picks the wrong starting table the query fails for lack of a table
that would have fitted comfortably.

**Measured.** BIRD databases hold 3–13 tables. Skipping retrieval there removed
one model call per question and contributed to the latency drop from 6.3s to
2.5s.

**Cost.** A few hundred extra tokens per question on small schemas. Cheap
relative to a wasted model call plus a repair round.

**Honest caveat.** 15 is a judgement, not a measured optimum. The right
threshold depends on schema width — fifteen tables with eight columns each is a
very different prompt from fifteen with sixty. It is configurable for that
reason.

## Why a fixed graph, not a tool-calling agent loop

**Decision.** The steps are a LangGraph state graph with edges fixed by the
engineer, not a model deciding what to call next.

**Reasoning.** Every question follows the same sequence. There is nothing for a
model to decide about the *order* of work, so handing it that decision buys
flexibility that is never exercised while costing:

- non-deterministic control flow, which is hard to test;
- unbounded model calls on a question that needs two;
- debugging through a framework's execution machinery rather than a stack
  trace.

The model is asked to do three things it is uniquely good at — pick relevant
tables, write SQL, phrase an answer — and nothing else.

**Where this would be wrong.** An open-ended task — "explore this dataset and
tell me what is interesting" — genuinely has no knowable step count. That is a
tool-calling loop's home ground, and if this project grows an investigation
mode, that mode should be built that way rather than bent into this pipeline.

**LangGraph is used; LangChain is not.** Orchestration is a compiled
`StateGraph` ([`agent_graph.py`](../src/sqlagent/agent_graph.py)), which buys
three things that matter here:

1. The Loop A / Loop B decision becomes a single conditional edge rather than
   logic repeated at each failure site. That is not hypothetical — the bug
   above was caused by exactly that duplication.
2. Checkpointing is available when human-in-the-loop work needs it.
3. The graph can be rendered, which makes the control flow reviewable rather
   than something you reconstruct by reading nested `try`/`except`.

The model *client* is a direct httpx call against Mantle's documented endpoint
rather than a LangChain provider wrapper — about 200 lines, and a wrapper would
add a dependency without removing any of it.

**The port was behaviour-preserving.** All 210 tests passed unchanged after
swapping the internals, which is the evidence that the two implementations are
equivalent rather than merely similar.

## Three safety layers, not one

**Decision.** Read-only role *and* SQL validation *and* read-only transaction.

**Why not just the role?** Because it is granted once and then trusted forever.
If somebody grants write access during an incident and forgets to revoke it,
the only protection is gone and nobody finds out until data is lost.

**Why not just validation?** Because it is code, and code has bugs — as the two
above demonstrate.

**What each catches that the others cannot:**

| Layer | Unique contribution |
|---|---|
| Read-only role | Survives any bug in our code |
| Validator | Enforces rules a role cannot express: mandatory `LIMIT`, table allow-lists, forbidden functions. Fails fast, with a message good enough to feed a repair loop |
| Read-only transaction | Survives a misconfigured role |

**Cost.** Under a millisecond of parsing per query.

## Parsing SQL instead of pattern matching

**Decision.** sqlglot, not regular expressions.

A regex for `DROP` fails in both directions:

```sql
SELECT 'DROP TABLE orders' AS note                        -- blocked, harmless
WITH gone AS (DELETE FROM orders RETURNING *) SELECT * FROM gone  -- allowed, destructive
```

That second statement is valid PostgreSQL. The outer statement genuinely is a
`SELECT`. Only walking the syntax tree catches it, and there is a test named
after this exact case.

## Fetching one row more than the limit

```python
fetched = cursor.fetchmany(row_limit + 1)
truncated = len(fetched) > row_limit
```

Without the extra row, a result of exactly 1000 rows is indistinguishable from
50,000 rows capped at 1000. The user would be shown a partial answer presented
as complete — a silent correctness failure, which is the worst kind.

Cost: one row.

## Deterministic fallback for table selection

**Decision.** If the model's table-selection reply cannot be parsed, fall back
to matching table names appearing in the question text.

**Why.** It keeps the agent working when the model misbehaves, and it makes the
unit tests independent of model behaviour — several pipeline tests drive the
fallback deliberately by returning garbage.

**Honest assessment.** The fallback is crude. It matches substrings and
singular forms and nothing else. It only has to produce a starting point,
because the graph walk does the real work from there.

---

## Sample rows: accuracy against privacy

**Decision.** Two rows per table by default, truncated to 100 characters,
disableable entirely.

**The trade, stated plainly.** Sample rows are real customer data. They travel
to the model provider and appear in anything logging prompts. In exchange, the
model learns that `status` holds `'active'` rather than `1`, and that dates are
real `DATE` columns rather than strings — facts the schema cannot convey and
which decide whether a `WHERE` clause matches anything.

**Mitigations built in.** Per-column exclusion, value truncation, and a
configuration that turns the feature off without breaking the pipeline.

**What is not built.** Automatic PII detection. Deciding which columns are
sensitive is a judgement about a specific database, and a heuristic that is
wrong in either direction is worse than an explicit list.

## Prompts as version-controlled source

**Decision.** Every prompt lives in `prompts.py`, not inline at call sites.

A prompt change is a behaviour change. It should appear in a diff, be
reviewable, and be measurable by re-running the benchmark. Burying prompt text
inside a function that also does HTTP makes all three impossible.

---

## Temperature zero

**Decision.** `temperature=0.0` everywhere.

The same question should produce the same SQL. Determinism makes caching
meaningful and benchmark runs reproducible. Variety has no value when there is
a correct answer.

---

## Testing against a real database

**Decision.** Integration tests run against real PostgreSQL in Docker, not
mocks.

Half of what the execution layer does is react to what the database says: which
SQLSTATE a missing table produces, whether a read-only transaction actually
refuses a `DELETE`, whether a statement timeout fires. A mock would assert my
beliefs about PostgreSQL rather than PostgreSQL's behaviour.

The tests skip themselves when no database is reachable, so `pytest` still
passes on a fresh checkout.

**Cost.** Docker as a development dependency. Worth it: the read-only
transaction test genuinely proves a `DELETE` is refused and the row is still
there afterwards.

## Quoting camelCase identifiers — found on a real application database

BIRD's schemas are all `snake_case`, so a whole class of failure was invisible
until the agent was pointed at a real Prisma-generated application database
(56 tables, 78 foreign keys).

**Symptom.** Roughly half the questions failed or needed a repair:

```
column oi.itemid does not exist
(hint: Perhaps you meant to reference the column "oi.itemId")
```

**Cause.** PostgreSQL folds unquoted identifiers to lower case. A Prisma column
called `itemId` must be written `"itemId"`; written bare it becomes `itemid`,
which does not exist. Prisma, TypeORM and Rails all generate camelCase columns
by default, so this is not an edge case — it is most application databases.

**Fix.** Render identifiers in the prompt exactly as they must be written,
quoting anything that would not survive folding, and quote them in the join
predicates too. A dialect rule was added as well, for columns the model invents
rather than copies — but showing the correct form is what does the work. The
model copies what it is shown far more reliably than it follows a rule.

**Measured on the real database**, same five questions:

| | Answered | Repairs |
|---|---|---|
| Before | 3 of 5 | 5 |
| After | **5 of 5** | **0** |

Latency fell too, since a repair costs a whole extra generate-validate-execute
cycle.

**Why the benchmark could not have found this.** Every BIRD schema is
snake_case. A test corpus shares the blind spots of whoever assembled it, and
only unfamiliar data finds them — the same lesson as the case-sensitivity bug
above, arriving from the opposite direction.

## Four interventions that did not work

Recorded because null results are cheap to repeat and expensive to rediscover.
All were measured paired — same 150 questions, same seed, same model — against
the run immediately before them. Run-to-run noise was separately measured at
**±0.7pp** (2 of 149 questions flip between identical runs), so these are real
nulls rather than noise swamping a small effect.

| Intervention | Paired result | Verdict |
|---|---|---|
| DISTINCT guidance in the system prompt | +7 / −6, p=1.000 | No effect |
| Dialect-specific SQL rules | +7 / −7, p=1.000 | No effect on SQLite; kept anyway (see below) |
| Value profiling, sampled | −5 questions, p=0.388 | Worse; had a real bug |
| Value profiling, exact DISTINCT | −2 questions, p=0.754 | Bug fixed, still no better, +44% tokens |

Cumulative effect of all four: **56.4% → 56.7%**.

### Why they failed, which is the useful part

The dialect experiment is the most instructive, because it **worked exactly as
designed and still did not help**:

| | Before | After |
|---|---|---|
| Queries using `CAST`/`REAL` | 21 | 28 |
| Queries using `IIF` | 1 | 8 |
| Of 26 questions whose gold uses `CAST`, we produced it | 17 | 22 |
| …and were correct | 16 | **14** |

The generated SQL moved *closer to gold syntactically* and got *less correct*.
That is the finding: the model already knows SQLite. The remaining failures are
semantic — wrong column, wrong grain, wrong reading of an ambiguous question —
and context-shaping does not touch them.

### Prompt edits are not local

The DISTINCT rule added two lines to the system prompt. It fixed 7 questions
that genuinely needed DISTINCT, and broke 6 — of which only **one** involved
DISTINCT at all. The other five were unrelated questions whose output shifted:
a date literal changed from `'1990'` to `'1990-12-31'`, a `CASE` began returning
`'Yes'` instead of `1`, one query came back empty.

Practical consequence: a prompt change cannot be reasoned about locally and must
be benchmarked, not inspected.

### The bug inside the failed experiment

Value profiling v1 inferred each column's distinct values from
`SELECT * FROM t LIMIT 200`. `LIMIT` without `ORDER BY` returns rows in physical
order, and real tables are clustered, so the sample was badly unrepresentative:

```
california_schools.frpm."County Code"
   claimed:  1 value    (the first 200 rows were all one county)
   actually: 58 values
```

**77% of the "this is the complete value list" claims were false** — 92 of 120.
The prompt was asserting something untrue, and a model that believes it writes
`IN (...)` filters that silently drop rows.

v2 asks the database directly, `SELECT DISTINCT col FROM t LIMIT n+1`, so a
short result *proves* completeness rather than inferring it. False-claim rate
fell to **0 of 66**, and accuracy recovered 1.3pp — still not beating plain row
sampling. The feature is kept, tested, and off by default.

### Why the dialect rules were kept despite measuring null

BIRD is SQLite-only, so the benchmark can measure one of the three dialect rule
sets and says nothing about the other two. Telling a MySQL user that `||` is
logical OR rather than string concatenation is correct regardless of what a
SQLite benchmark reports. Cost is roughly 60 tokens per request.

This is a deliberate exception to "measure everything": the measurement does not
cover the case the code exists for. It is flagged rather than hidden.

## Carrying a conversation, and what gets carried

A question asked by a person is usually not the first one. The second is
"and for April?", the third "break that down by city". Neither is a question
about a database on its own — they only mean something relative to the turn
before, and an agent that answers each question in isolation cannot answer
either of them.

**What a turn keeps: the question and the SQL.** Not the answer prose, not the
result rows.

- The SQL is the precise, compact record of what was measured. "and for April?"
  becomes answerable the moment the model can see
  `SELECT count(*) FROM orders WHERE "createdAt" >= '2026-03-01' ...` — it has
  to change one literal.
- The answer says the same thing less precisely in more tokens.
- The rows could be thousands, could be personal data, and would crowd the
  schema out of the prompt. The schema is what makes the next query correct.

**Bounded at four turns.** Turn 30 rarely constrains turn 31, and carrying
everything means the prompt grows without limit until the part that matters is
squeezed out. Older turns stay in the store and stay visible in the UI; they
just stop being fed to the model. Deeper chains almost always restate the
subject anyway ("okay, now for refunds"), which re-anchors the context without
needing history.

**Failed turns are carried too, marked as failed.** A model shown a clean
history repeats the mistake it cannot see.

**History also seeds retrieval.** "Break that down by city" contains no table
name, so seed selection has nothing to match on and the graph walk starts from
nowhere. The previous turns' SQL names the tables outright, which is a better
starting point than anything derivable from the question text. Matching is
whole-word against tables that actually exist, so a column called
`orders_total` cannot be mistaken for the `orders` table.

**With no history, the prompt is byte-identical to what it was before this
existed** — there is a test asserting exactly that. An empty history renders as
an empty string, not as "no previous questions". That is what keeps every
benchmark number already recorded comparable.

Measured on the real production database, a three-turn thread:

| Turn | Question | SQL generated |
|---|---|---|
| 1 | How many orders are there in total? | `SELECT COUNT(*) FROM orders` |
| 2 | and how many of those were delivered? | `SELECT COUNT(*) FROM orders WHERE status = 'DELIVERED'` |
| 3 | break that down by month | `SELECT DATE_TRUNC('MONTH', "createdAt"), COUNT(*) FROM orders WHERE status = 'DELIVERED' GROUP BY ...` |

Turn 3 carried forward both the table *and* the filter established in turn 2,
with zero repairs.

**Where the state lives: the server, not the browser.** A reload must not lose
the thread, and the turns fed to the model then come from the same record the
history view shows, so the two cannot disagree about what was asked. The client
never invents a thread id — the server creates the thread on the first question
and returns it, so there is no window in which the browser holds an id the
server has not heard of. An unknown id is treated as a request for a new thread
rather than a 404: a stale id in a browser tab should cost the user nothing.

**What conversation is not.** It is not memory across threads, not a learned
profile, and not a summarisation loop. It is a bounded window of recent turns
rendered into the prompt. Anything longer-lived — a glossary, cached recurring
questions, cross-session preferences — remains unbuilt.

## Six defects found by using it on real data

A long session against the production database surfaced failures that 500 benchmark
questions did not, because the benchmark asks one-shot questions and scores
result sets — it cannot see a conversation drift, and it never reads the English
sentence at all.

### 1. A fabricated UUID, and why the design caused it

    Q: I need an item that has been repeatedly ordered
    A: ... "Grilled Chicken Bowl (250gm)", ID a1b2c3d4-0000-4000-...
    Q: what is the name of the item with that ID
    -> SELECT name FROM items WHERE id = 'e5f6a7b8-1111-4111-8111-111111111111'

The model invented a UUID. Not carelessness — the history carried the previous
turn's **SQL**, and that SQL contains no id. The id existed only in the row the
query *returned*, which the original design deliberately excluded. "That ID"
had no referent, and a plausible-looking UUID filled the gap.

Worse than an error: the fabricated id was well-formed, the query executed, a
real row came back, and the answer reported it faithfully. Nothing downstream
could tell it was wrong.

**Fix:** carry the result forward when — and only when — it is small enough to
be a lookup (3 rows × 5 columns). All-or-nothing: carrying the first three rows
of a hundred would let the model treat a truncated sample as a complete answer.
Larger results carry a row count and nothing else, so the turn cannot read as
"the query found nothing".

This narrows the store's original "no result rows, ever" rule. The bound is what
keeps it honest: "list every customer" still stores nothing.

### 2. An answer that named the wrong thing

Separately, a one-row result naming one item was described in the answer as a
different dish entirely. The SQL was right, the row was right, the sentence was
false.

**Fix:** `guards/faithfulness.py`, a mechanical check between the answer and the
rows it claims to describe. Two conservative rules — a figure of three or more
digits that appears in neither the results nor the question, and a small result
whose text values the answer failed to quote. A failure triggers one regenerate
with the specific offending value named, because a model told "that is wrong"
rewrites the sentence and keeps the invention.

Deliberately not checked mechanically: whether a qualifier is justified by the
WHERE clause. That needs the SQL's semantics, not its text.

### 3. A qualifier the query never applied

Asked for the most-ordered items, the agent returned an unfiltered list and
described it as "the vegetarian items". The list contained Chicken Tikka Roll
and Grilled Chicken Bowl, both `isVegetarian = false`.

**Fix:** a rule in `ANSWER_SYSTEM_PROMPT` — describe the results using only the
filters the query actually applied, *even if the user asked for more*. Say what
was measured, not what was wanted.

### 4. A correction treated as an addition

    Q: I told you it should be veg
    -> 0 rows

The vegetarian filter was added to a query still pinned to one specific item id
from two turns earlier. The user's correction meant "search the vegetarian
items"; it was read as "check whether that one item is vegetarian".

### 5. …and the opposite failure, in the same session

    Q: for the orders that were actually delivered      (during a revenue analysis)
    A: There were 2,147 orders that were actually delivered.

Here the restriction replaced the analysis instead of narrowing it.

**Fix for both:** explicit carry-forward rules appended to the history block.
The two failures are opposites, which is why both rules are needed — the model
has no default sense of which parts of a previous turn are the subject and which
were incidental, and left to itself it guesses inconsistently.

Replaying the exact failing sequence after the fixes: turn 2 produces the real
UUID and the correct name; turn 3 returns the correct vegetarian item instead of
zero rows.

### 6. Money reported 100× too large — **not fixed**

`order_items.price` stores paise: a `12500` is ₹125.00. Revenue totals were
reported as raw integers — "₹1,234,500" where the truth is ₹12,345 — and in
another turn the same kind of figure was labelled `$`, for an Indian business.

This is not a bug that can be fixed in a prompt. Nothing in the schema says the
column is paise; the type is `integer` and the name is `price`. A heuristic
("large integers in money-shaped columns are probably minor units") would be
wrong on any database that stores rupees directly, and being confidently wrong
about money is the failure being fixed.

It needs a **glossary**: per-database declarations — this column is paise,
revenue means this expression, `cart_items` is not `order_items` — injected into
the prompt. That is the next thing to build, and it is the same mechanism that
would fix the related ambiguity seen in the same session, where a follow-up
silently switched from `order_items` to `cart_items`, which are
different questions.

## The optional layers, and why each is off

Six features exist as toggles rather than as always-on behaviour. That is not
indecision — each buys accuracy or safety with latency and tokens, and the only
honest way to settle that trade is to measure it. A toggle is how the number
gets to decide instead of the design document.

| Toggle | Default | What it costs | What it buys |
|---|---|---|---|
| `use_critic` | off | 1 model call per question | Catches queries that are safe, cheap and about the wrong thing |
| `vote_samples` | 1 (off) | N× generation calls | Majority over N samples; helps where the model is guessing |
| `quality_tier` | `fast` | — | `thorough` turns on both of the above |
| `prescreen_input` | off | 1 model call per question | Screens the question; defends the conversation, not the database |
| `ambiguity_handling` | `best_effort` | 1 call + a round trip to the user | Asks instead of guessing when a question has two defensible answers |
| `decompose_questions` | off | 1 call, then N sub-questions | Answers a question that is really several questions |

### They are on the page, not in a config file

Each toggle is settable **per question**, from a panel on the homepage, and the
choice persists per browser.

The reason is that the trade each one makes — latency and tokens against a
better chance of being right — depends on the *question*, not on the
deployment. "Check this one carefully, it is going in a board pack" is a
decision made while asking. An environment variable makes it once, by whoever
deployed the server, for every question anyone ever asks.

Measured on the production database, the same question three ways:

| Setting | Model calls | Time | Tokens |
|---|---|---|---|
| defaults | 3 | 3.9s | 9,956 |
| `use_critic` | 4 | 3.6s | 18,459 |
| `quality_tier: thorough` | 6 | 5.2s | 36,373 |

**Every toggle states its cost next to the control.** One offered without a
price gets switched on by everyone, who then conclude the tool is slow.

**The list is served, not hardcoded in the client.** The defaults are a server
decision a deployment may change, and the explanations belong beside the code
implementing them — a hardcoded list means a new toggle is invisible until
someone updates the frontend, and an explanation that drifts with no test to
catch it.

**What is deliberately not exposed: an allow-list, not a denylist.** Only the
seven quality settings can be overridden. The row cap, the timeouts, the models
and the database URL stay server-side, and `config.OVERRIDABLE` enforces that
independently of the request model. An allow-list fails closed — a setting added
to `Settings` is not remotely settable until someone deliberately adds it — where
a denylist would make every new setting client-controllable by default, which is
how a row cap ends up being something the browser can change.

**"Unset" and "off" are different states.** A field omitted means "follow the
server"; `false` means "turn this off for this question". Without that
distinction a user would be pinned to whatever the default happened to be the
day they first opened the panel, and "Reset to defaults" could not exist.

Two of these deserve their reasoning stated rather than summarised.

**Why `best_effort` is the default, uncomfortably.** An automated benchmark
cannot answer a clarifying question. With `ask_human`, every ambiguous BIRD
question would stall, and the measured accuracy would describe a system nobody
is running. So the configuration that *scores* well is not the one that serves a
person best, and only one of them can be the default. The benchmark won.

**Why the pre-screen is the weakest layer, deliberately.** It does not defend
the database — the read-only role, the validator and the read-only transaction
do that, and none of them can be talked out of it by a cleverly-worded question.
What it catches is exfiltration through a perfectly legitimate SELECT ("list
every customer's email"), instruction override that now *persists* because
conversations carry history, and probing for the prompt or credentials. It fails
open on error, because deny-on-error would turn a throttled model into an
outage.

### Two bugs that only integration tests could have caught

Every toggle defaults to off, which meant each one's unit tests exercised the
module in isolation while the *wiring* — the graph node, the routing, the import
— was never executed by the suite at all.

Two imports in `agent_graph` were missing for a while and the whole suite passed,
because the code using them only runs when a flag nobody had flipped is on. A
linter caught it. The tests should have.

Turning each flag on and driving a real question through the real graph then
immediately found a second, worse one: a cached statement that failed routed
into `widen_schema`, which reads a neighbourhood a cache hit never builds —
a `KeyError` in production, reachable the first time a cached query went stale.
`tests/test_toggles.py` exists because of both.

## Caching the SQL, never the rows

The statement is cached. The results never are.

Caching results would be faster still and wrong almost immediately: the database
is live, and "how many orders today" served from a cache is a stale number
presented as a current one. Caching the SQL skips the expensive part — two or
three model calls — while the query re-runs against real data every time. A hit
is fresh *and* fast.

It also keeps every safety property. A cached statement goes through the
validator, the cost gate and the read-only transaction exactly like a generated
one. The cache sits in front of the model, not around the guards.

The key includes the schema version and a hash of the glossary, because both
change what the right SQL is. Without the glossary in the key, editing "price is
in paise" would appear to do nothing for every question already asked.

Follow-ups are never cached. "And for April?" means whatever the previous turns
made it mean, and two threads can give the same fragment completely different
meanings.

## Exposing the agent over MCP

Another assistant may need a figure out of this database. The alternatives are
worse than a protocol:

* Hand it credentials and let it write SQL — which discards the read-only role,
  the validator, the cost gate and the row cap in one move.
* Wrap the HTTP API by hand, once per client.

Over MCP the caller gets the *questions*, not the connection. Three tools:
`ask_database`, `list_tables`, `describe_table`. **There is deliberately no tool
that takes raw SQL** — offering one would reduce this to a database proxy and
hand the calling model exactly the freedom the validator exists to remove. A
test asserts that no tool's schema has an `sql` or `query` parameter.

## What is not built, and why

Being explicit about absences is more useful than implying completeness.

| Not built | Why |
|---|---|
| Multi-tenancy | Single database per process. Cache and memory keys would need tenant scoping to avoid cross-tenant leaks |
| Charts | The API returns typed rows, so a client can. The agent does not choose visualisations |
| Automatic PII detection | See above — a wrong heuristic is worse than an explicit list |
| CSV / spreadsheet upload | Files carry no foreign keys, so the graph has nothing to walk. Would need inferred or declared relationships |
| A judge for answer quality | Execution accuracy measures the SQL. The faithfulness guard checks the sentence against the rows, but whether it is *good* is unmeasured |
| Multi-agent orchestration | A manager delegating to analyst/research/compute sub-agents. The pipeline is engineer-planned and does not need a planner; a sandboxed code interpreter is a separate security project |
| Drift detection | Needs a baseline over time, which needs the thing to have been running over time |
| Automatic glossary inference | A wrong declaration is visible in a file; a wrong inference is a silent multiplication buried in generated SQL |

## Current state, honestly

**Full BIRD mini-dev, all 500 questions, `qwen3-coder-480b`:**

| Metric | Value |
|---|---|
| Execution accuracy | 57.8% (289/500) |
| Correct first attempt | 56.6% |
| Needed a repair | 3.8% |
| Mean per question | 2.6s |
| Wall clock for the full run | 361s at 6 workers |
| Tokens | 1.25M in / 55k out |
| simple / moderate / challenging | 70.3% / 55.6% / 45.1% |

**Head-to-head with the previous implementation**, same 500 questions:

| | Accuracy | Latency |
|---|---|---|
| sql-agent | **57.6%** | **2.61s** |
| Aperture | 53.0% | 7.51s |

+4.6pp, p = 0.022 (58 won, 35 lost), 2.9× faster, better at every difficulty.

**What that number does and does not mean.** The two runs use different models,
so it is not a clean measure of the pipeline. The same-model comparison at
n=150 put the pipeline's own contribution at +3.4pp, p = 0.458 — not
significant. The honest reading is that most of the gain is model selection,
and the architectural work bought latency (2.9×) rather than accuracy.

Three of the 500 gold queries fail to execute at all (`gold_sql_failed`), so
the practical ceiling is 497.

### Tested at scale — the retrieval design holds

The PostgreSQL distribution of BIRD merges all 11 databases into a single
`public` schema: **75 tables, 87 foreign keys**, real data. Restoring it gives
the measurement that was missing, because with one SQLite file per database the
agent sees 3–13 tables and skips retrieval entirely.

Same 150 questions, same model, the only difference being whether the schema
arrives pre-filtered:

| | Accuracy | Latency | Model calls |
|---|---|---|---|
| Per-database SQLite (3–13 tables, retrieval skipped) | 57.0% | 2.53s | 2.0 |
| Merged PostgreSQL (75 tables, retrieval engaged) | **56.4%** | 3.39s | 3.0 |
| Cost of retrieval | **−0.7pp** (p = 1.000) | +0.86s | +1 |

Being handed exactly the right 3–13 tables is worth **less than one percentage
point** over finding them among 75.

The failure breakdown is the stronger evidence. Of 66 failures on the 75-table
schema, **one** was caused by retrieval failing to supply a needed column;
every other was a wrong answer from a query built on correctly-retrieved
tables. The graph walk is not the bottleneck.

This also exercises the PostgreSQL dialect path end to end, which BIRD's
SQLite-only distribution otherwise leaves untested.

**What is still untested:** a schema large enough that the *seed selection*
prompt itself becomes unwieldy. At 75 tables the table-name list is a few
hundred tokens. At 500 it would not be, and a different approach — embedding
the table list, or a hierarchical narrowing — would likely be needed.
